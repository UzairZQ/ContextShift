# ContextShift v1.1 - Attention Awareness

> Discussion draft. This document defines a product direction for research and
> review; it is not an implementation commitment.

## Working Idea

ContextShift v1.1 could help people understand where their mobile attention
goes, then connect that information with the context the app already knows:
tasks, build and reduce habits, focus sessions, mood, journal entries, and local
JARVIS memory.

The goal is not to block apps or shame people for using their phones. The goal
is to turn vague feelings such as "I wasted the whole evening" into a useful,
private reflection:

- What consumed my attention?
- When did it happen?
- What did I intend to do instead?
- Is there a small adjustment worth trying tomorrow?

## Product Promise

**See your attention clearly. Choose what deserves it next.**

ContextShift should help the user move from awareness to an intentional next
action. It should not become another dashboard that reports screen time without
helping the user respond to it.

## Why It Fits ContextShift

The existing app already brings together:

- Tasks and active intentions
- Build and reduce habits
- Focus-session history
- Mood check-ins and journal entries
- Local behavior events
- Home and AI Analysis summaries
- On-device Gemma context and conversation memory

App-usage information could become one more local context signal. This would let
ContextShift answer questions such as:

- "How was my attention today?"
- "Did I focus more on days when I used Instagram less?"
- "When do I usually start scrolling?"
- "What could I change tomorrow without making an unrealistic plan?"

JARVIS must describe observed patterns, not present correlations as proven
causes.

## Scope for v1.1

### 1. Permission and setup

- Explain why Usage Access is needed before opening Android Settings.
- Make the feature fully optional.
- Let the user select which apps matter to them.
- Clearly state that usage information stays on the device.
- Keep the rest of ContextShift usable when permission is declined or revoked.

### 2. Attention overview

Show a compact daily view with:

- Total time in user-selected apps
- Time per selected app
- Change compared with the user's recent baseline
- Usage during a user-defined late-night window
- A simple daily attention intention, such as "Keep social apps under 45 min"

The first version should avoid an overloaded digital-wellbeing dashboard.

### 3. AI context

Add a compact `attention` section to the existing local context snapshot. A
possible shape is:

```json
{
  "attention": {
    "selected_minutes_today": 64,
    "daily_intention_minutes": 45,
    "seven_day_average_minutes": 71,
    "late_night_minutes": 18,
    "apps": [
      {
        "label": "Instagram",
        "minutes_today": 42
      },
      {
        "label": "YouTube",
        "minutes_today": 22
      }
    ]
  }
}
```

Only the smallest useful summary should enter the Gemma prompt. Raw usage
events and a complete installed-app inventory should not be injected.

### 4. AI Analysis

The Home insight and AI Analysis screen should read from the same attention
summary source.

Useful insight:

> You spent 18 minutes more than your usual Tuesday average in selected social
> apps, mostly after 10 PM. Your focus session was completed earlier in the day.
> Tomorrow, try moving the German practice before your usual late-evening scroll.

Unhelpful insight:

> Your productivity score is bad. Stop using Instagram.

Insights should be:

- Concrete and grounded in local data
- Neutral rather than moralizing
- Brief enough to scan
- Honest when there is not enough history
- Focused on one realistic next experiment

### 5. Intentional replacement

ContextShift may suggest an existing task, habit, focus session, or journal
prompt as an alternative action. This happens inside ContextShift; v1.1 does not
interrupt, overlay, lock, or block another app.

Examples:

- Start a 10-minute focus session for the next active intention
- Practice a two-minute version of a build habit
- Check in on a reduce habit
- Write a short note about what triggered the scrolling session

## Explicit Non-Goals

Version 1.1 will not:

- Block or lock other apps
- Use an Accessibility Service to watch or control app launches
- Draw overlays on top of other apps
- Request broad installed-app visibility without a proven need
- Upload app-usage information to a ContextShift server
- Rank the user with a universal productivity score
- Label every minute of entertainment as wasted
- Claim that app usage caused a mood or focus outcome

## Privacy Principles

- Usage tracking is opt-in and can be disabled at any time.
- Data remains device-local and follows the existing offline-first approach.
- Permission education must appear before the system permission screen.
- Store goals and compact summaries only when persistence creates clear value.
- Prefer user-selected apps over collecting a broad app inventory.
- Never include package names, raw events, or app-usage history in crash logs.
- Update the in-app Privacy page and Play Store Data safety declaration before
  release.

## Technical Direction to Research

Android provides usage history through `UsageStatsManager` after the user grants
Usage Access in system settings. A likely implementation shape is:

```text
Android UsageStatsManager
        |
        v
App-owned platform channel
        |
        v
Attention repository/service
        |
        +--> Shared daily attention summary
        |       +--> Home
        |       +--> AI Analysis
        |
        +--> ContextProvider compact attention payload
                |
                v
          On-device Gemma
```

Research is still required for:

- Reliable foreground-time calculation across supported Android versions
- Session-count accuracy and whether it is useful enough to expose
- App labels and icons without unnecessary package-visibility permissions
- Battery cost and refresh frequency
- Midnight, timezone, and daylight-saving boundaries
- Xiaomi and other OEM behavior
- Permission-revocation handling
- Data retention and database migration design
- Google Play disclosure and Data safety requirements

## Possible Local Data Model

This is a starting point, not a final schema.

### `AttentionPreference`

- Feature enabled
- Daily intention in minutes
- Late-night window
- Selected package identifiers
- Insight and reminder preferences

### `AttentionDailySummary`

- Local calendar date
- Total selected-app minutes
- Per-app minute summaries
- Late-night minutes
- Last refresh time

Raw operating-system events should not be copied into Drift unless later
research proves that the product cannot work without them.

## Delivery Phases

### Phase 1 - Research prototype

- Read usage data on a physical Android device
- Validate permission setup and revocation
- Compare totals with Android Digital Wellbeing
- Measure battery and refresh behavior
- Test Xiaomi plus at least one other Android manufacturer

### Phase 2 - Private MVP

- User-selected apps
- Daily and seven-day usage summaries
- One daily attention intention
- Shared attention summary for Home and AI Analysis
- No Gemma integration until the underlying totals are trustworthy

### Phase 3 - Local intelligence

- Add compact attention context to `ContextProvider`
- Generate neutral, evidence-based observations
- Suggest one existing ContextShift action
- Add prompt-size and missing-history safeguards

### Phase 4 - Release hardening

- Permission and privacy copy
- Database migration tests
- Timezone and day-boundary tests
- Performance and battery checks
- Play policy review
- Physical-device regression testing

## Success Criteria

The feature is useful when:

- Daily totals are close enough to Android Digital Wellbeing to be trusted.
- The user understands why permission is requested.
- Disabling permission does not break the app.
- Home, AI Analysis, and JARVIS use the same source of truth.
- The AI references real values and clearly handles insufficient history.
- The feature adds negligible idle battery and memory cost.
- The user receives one useful adjustment rather than a wall of statistics.

## Questions for the Next Discussion

1. Should users select distracting apps manually, or should ContextShift first
   show observed apps and ask them to choose?
2. Should the main goal be a daily minute limit, a number of sessions, a
   late-night boundary, or a combination?
3. How many days of history are needed before JARVIS may describe a pattern?
4. Should entertainment be treated neutrally unless the user explicitly marks
   it as unwanted?
5. Should attention appear as a new module, inside AI Analysis, or as a small
   addition to the existing Home context?
6. Should v1.1 include notifications, or remain reflection-only for its first
   release?
